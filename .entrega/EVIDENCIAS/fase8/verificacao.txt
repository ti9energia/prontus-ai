## Bug real encontrado ao preparar os alvos autenticados
A chave de API "de desenvolvimento" semeada (`src/lib/data/store.ts`,
`DEV_KEY_HASH`) tinha um hash placeholder de 62 caracteres — nem sequer um
sha256 válido (que tem 64), e NÃO era o hash de `sk_test_auronis_dev` como o
comentário afirmava (verificado: sha256 real = `e0a766a4...`, seed antigo =
`a3e4f9a2...`, 62 chars). Consequência: a chave semeada nunca autenticava, e
em modo produção (`next start`, onde o atalho `sk_test_*` fica desligado) a
API pública v1 inteira ficava inacessível com os dados semeados. Corrigido:
hash agora é o sha256 real de `sk_test_auronis_dev`. É a superfície de DEMO
(mesma fronteira de confiança do login DEMO_MODE — o token só destranca o
dataset de demonstração compartilhado, e um deploy real usa Postgres onde esse
seed não se aplica). O teste `api-key-auth.test.ts` que "achava a chave pelo
hash semeado" codificava o hash quebrado — agora deriva o hash do token real,
virando uma prova de verdade (guarda de regressão do bug da chave morta).

## Cenários e thresholds (k6/lib/config.js)
- smoke: 1 VU/30s — erro <1%, p95<600ms, checks>99%
- load: ramp→20 VUs, sustenta 1min — erro <2%, p95<1200ms, p99<2500ms
- stress: ramp→150 VUs — erro <15%, p95<5000ms (fora do CI por padrão; ver README)
- spike: 5→120 VUs súbito→5 — erro <10%, p95<4000ms
Thresholds calibrados para o runner compartilhado de 2 núcleos + adapter
in-memory, não são SLO de produção (framing honesto, igual ao Lighthouse da
FASE 6). Números de produção reais: apontar `-e BASE_URL=<deploy>` na
verificação conjunta (FASE 12).
