# DECISÕES

## 2026-07-02 — FASE 7: 1º run real do E2E achou 3 bugs de produção genuínos (34/49 falharam) — corrigidos, não contornados
- **O que aconteceu:** o primeiro run do job `e2e` no GitHub Actions (PR #57, run 28602783913) rodou de verdade — 23m59s, 49 testes reais em Chromium headless — e 34 falharam. Isso é exatamente o valor da FASE 7: como nenhuma fase anterior jamais renderizou estas páginas num navegador real (diretiva do dono: sem servidor local até agora), bugs invisíveis a typecheck/lint/build/vitest só podiam aparecer aqui.
- **Bug #1 (raiz, o maior): `isLanding` em `src/app/[locale]/layout.tsx` usava denylist, não allowlist.** A lógica era `!url.includes('/app') && !url.includes('/login')` para decidir se a rota recebe o catálogo de mensagens FILTRADO (só `landing/common/nav/pricing/faq/meta/pwa`, por tamanho de bundle) ou o completo. Isso classificava `/signup`, `/onboarding`, `/checkout` e `/owner` como "landing" por omissão — nenhuma dessas 4 rotas jamais foi listada. Resultado real em produção: essas 4 páginas inteiras rodavam com o catálogo ERRADO, e qualquer `useTranslations('auth'|'onboarding'|'checkout'|'owner')` dentro delas lançava `MISSING_MESSAGE` no servidor. **Corrigido:** trocado para uma allowlist expressa de rotas de produto (`PRODUCT_PATHS`), que falha seguro — uma rota nova esquecida aqui cai no catálogo COMPLETO (bundle um pouco maior), nunca mais quebra silenciosamente.
- **Bug #2 (agravante): `error.tsx` (o error boundary de toda rota `[locale]`) também dependia de uma mensagem fora do allowlist.** `HeroDemo` (demo animada do hero da landing) usa `useTranslations('encounter')` — namespace real, reaproveitado da tela clínica de consulta — mas `encounter` também não estava no allowlist da landing, então `HeroDemo` lançava `MISSING_MESSAGE` a cada re-render (a demo anima via `setInterval`/estado, então repetidamente). O `error.tsx` deveria capturar isso e mostrar um fallback estável — só que `error.tsx` TAMBÉM chama `useTranslations('notFound')` para o link "voltar ao início", e `notFound` também estava fora do allowlist. Resultado: o próprio fallback de erro quebrava ao tentar renderizar, então a página nunca estabilizava — Playwright via o botão de CTA sendo "detached from the DOM, retrying" em loop até estourar os 45s de timeout. Isso explica por que até testes sem relação aparente com signup (footer, FAQ, idioma, CTA da landing) falharam: instabilidade de página inteira, não um seletor errado. **Corrigido:** `encounter` e `notFound` adicionados ao `LANDING_NS`.
- **Bug #3 (achado por cálculo, não só pelo teste): contraste insuficiente em botões brancos-sobre-cor no design system inteiro.** O axe (`@axe-core/playwright`) acusou `color-contrast` sério em botões `type="submit"` de landing/login/signup — `bg-brand-600` (#00A8A2) com texto branco mede 2.95:1, abaixo do mínimo AA de 4.5:1. Como `buttonVariants` (`src/components/ui/button.tsx`) é o primitivo COMPARTILHADO de botão do app inteiro, o mesmo cálculo (via script Node com a fórmula real de luminância relativa do WCAG) revelou que `accent` (1.81:1) e `danger` (3.91:1) tinham o mesmo problema, não pego pelo axe só porque nenhuma página varrida neste run os usa visivelmente. **Corrigido:** `primary` → `bg-brand-800`/`hover:bg-brand-900` (6.77:1), `accent` → `bg-accent-700`/`hover:bg-accent-800` (5.36:1), `danger` → `bg-danger-fg`/`hover:brightness-90` (5.41:1, reaproveitando o token `fg` já existente em vez de inventar cor nova) — todos com margem real acima de 4.5:1, não um passe raspando o limite.
- **Por que não é regressão desta fase (mas com uma ressalva honesta):** `git log -p` em `layout.tsx` mostra que `LANDING_NS`/`isLanding` nasceram no commit `7161808` ("Block 19: i18n namespace filter", 2026-06-30), bem antes desta pipeline (FASE 0 começou 07-01) — o denylist (`!url.includes('/app') && !url.includes('/login')`) nunca listou `/signup`/`/onboarding`/`/checkout`/`/owner`, e `encounter`/`notFound` nunca estiveram no allowlist, desde a origem. `button.tsx`'s paleta de botões vem do commit inicial `0f6fa4f` (2026-06-24), também pré-pipeline. **Ressalva:** a FASE 6 desta pipeline (`e0ae907`) TOCOU essa mesma linha de `LANDING_NS` (adicionou `'pwa'`) sem notar os buracos de `encounter`/`notFound` — porque a correção da FASE 6 também foi reativa a um bug achado por leitura de código (PWARegister fora do provider), não por execução em navegador real. Ou seja: mesmo tocando o arquivo, nenhuma fase anterior TINHA COMO ver este bug especificamente, porque nenhuma delas renderizou a página de verdade — exatamente a lacuna que a FASE 7 fecha.
- **Por que corrigir agora em vez de só documentar em PENDENCIAS.md:** o princípio "corrigir antes de avançar" — e o próprio propósito de ter a suíte E2E é ficar verde contra um app que funciona de verdade, não contra um app com bugs conhecidos e ignorados. Documentar sem corrigir teria sido exatamente o tipo de "teatro" que o pipeline proíbe.
- **Prova:** typecheck ✅ lint ✅ 349 testes ✅ build prod exit 0 ✅ localmente após as correções; run 2 do CI (após push) é a prova de execução real — ver EVIDENCIAS/fase7/verificacao.txt para os números antes/depois.

## 2026-07-02 — FASE 7: GitHub Actions como ambiente de execução do E2E (não local)
- **Tensão:** o pipeline exige prova por execução real ("sem teatro" — não afirmar que algo funciona sem rodar); o dono pediu para não subir servidor local nesta rodada, com a verificação ao vivo reservada para uma sessão conjunta após a FASE 12.
- **Resolução:** o `webServer` do Playwright (`playwright.config.ts`) sobe o `next start`, espera `/api/health` responder, roda a suíte inteira e derruba o processo sozinho — esse ciclo de vida completo roda DENTRO do runner do GitHub Actions (job `e2e` novo em `ci.yml`), nunca na máquina local. Isso entrega prova de execução genuína (não é leitura de código, é clique-e-resposta real via Chromium headless) sem contradizer "não precisa subir porta nem nada" — a porta sobe e morre num runner efêmero na nuvem, não na máquina do dono.
- **Por que não esperar até a FASE 12:** a suíte E2E É o mecanismo de prova da FASE 7; adiar a execução tornaria a fase inteira "planejada, não verificada" por 5 fases seguidas (8–12), quebrando o princípio de não carregar pendências entre fases. CI resolve isso sem violar a diretiva do dono.
- **Efeito colateral corrigido:** a suíte completa (49 testes) gera ~19 chamadas a `/api/auth/signup` e ~8 a `/api/auth/login` na mesma execução — o suficiente para os rate-limiters de produção (5/15min, 8/15min) derrubarem a própria suíte em cascata. Resolvido tornando os limites configuráveis via `E2E_MAX_LOGIN_ATTEMPTS`/`E2E_MAX_SIGNUP_ATTEMPTS` (só setados em `playwright.config.ts`'s `webServer.env`; os defaults de produção — 5/8 — não mudam).
- **Precedente para FASE 8 (k6):** mesma tensão vai se repetir para testes de carga. Plano: tentar o mesmo padrão (rodar dentro do runner do CI) antes de considerar deferir para a verificação conjunta.

## 2026-07-02 — Incidente: 3 agentes de UI em paralelo retornaram sem produzir arquivos
- Delegados 3 agentes em background para construir UI de signup/onboarding/checkout (specs completas, contratos de API prontos). Os três voltaram com mensagem atípica: "You've hit your session limit · resets 5am (America/Fortaleza)" e, em dois casos, aviso de que o classificador de segurança não pôde revisar o trabalho.
- **Verificação:** `git status` após os três terminarem mostrou ZERO arquivos novos/alterados além dos meus próprios — nenhuma das três frentes produziu qualquer artefato persistido, apesar de reportarem 62–91 chamadas de ferramenta cada. Conclusão: o limite de sessão interrompeu os agentes antes de qualquer escrita durável (ou o trabalho não foi persistido por algum outro motivo) — não confiei no "resultado" reportado, tratei como se nada tivesse sido feito.
- **Decisão:** não tentei novos agentes em background (risco de bater no mesmo limite outra vez, desperdiçando mais). Constatei que o reset (5h em Fortaleza, UTC-3) já tinha passado no horário corrente (~14h UTC) — o próximo reset ficaria a ~17-18h de distância. Passei a construir as três telas (signup, onboarding, checkout) diretamente eu mesmo, sequencialmente, reaproveitando o mesmo contexto/specs que dei aos agentes. Terminado com sucesso: build de produção com exit code 0 (confirmado via Bash — o PowerShell reportou 255 por engano, interpretando uma linha de warning do Next.js como erro), typecheck/lint limpos, 349 testes de backend seguem verdes.
- **Aprendizado registrado:** ao delegar tarefas grandes (>10min) em paralelo, verificar sempre `git status`/diff real após a conclusão antes de confiar no texto do resultado — especialmente quando a mensagem final foge do padrão esperado.

## 2026-07-02 — FASE 5: escopo do signup/onboarding frente ao modelo de dados atual
- **Achado:** todo o núcleo clínico (`listPatients/listEncounters/notes/guides/labOrders`) é um dataset global único, não segmentado por `orgId` — é assim para TODAS as identidades hoje (owner, médico-teste, demo), não é uma lacuna introduzida pelo signup. Só as entidades voltadas ao dono (`tenants`, `users` via `orgId`, `apiKeys`) já são multi-tenant de verdade.
- **Decisão:** o signup cria Tenant + User REAIS (persistidos, aparecem no painel do dono, login funciona de verdade); o onboarding persiste progresso REAL por org; o checkout cria Order/Subscription REAIS por tenant. Ao entrar em `/app`, o novo usuário vê o mesmo workspace clínico de demonstração compartilhado que médico-teste/demo já veem hoje — isso é consistente com o produto atual, não uma mentira nova.
- **Por que não isolar dados clínicos por tenant agora:** exigiria re-arquitetar dezenas de funções do store (patients/encounters/notes/guides/labs) que hoje assumem um único contexto — uma migração de arquitetura própria, desproporcional ao pedido desta fase (integrações pré-prontas). Registrado como fronteira consciente em `PENDENCIAS.md`, candidato a uma fase própria se o dono priorizar multi-tenancy clínica completa.
- A sessão (`useSession()`) já reflete a identidade real de quem logou (nome/e-mail) na top-bar — só o *conteúdo clínico* de demonstração é compartilhado, a identidade de quem está logado é sempre verdadeira.

## 2026-07-01 — FASE 1: entradas públicas por módulo com split de runtime
- Cada módulo de `lib/` expõe barrel `index.ts` (isomórfico) e, quando preciso, `server.ts` (Node-only) / `client.tsx` (hooks React). Motivo: um barrel único puxaria `node:crypto`/SDKs para o client e React para o edge middleware.
- `src/lib/auth.ts` (hooks client) movido para `src/lib/auth/client.tsx` para o diretório `lib/auth/` virar o módulo canônico.
- Import profundo cruzado agora é **erro de lint** (`no-restricted-imports`); testes internos do módulo são isentos.
- `lib/config` é a única porta para `process.env` (getters lazy — testes que mutam env seguem funcionando; `NEXT_PUBLIC_*` com acesso literal para inline no client).
- `.env.example` passou a documentar TODAS as vars (DB, ASR, Memed, ICP, WhatsApp) — antes só existiam em comentários de código.
